## 为什么选

矢量地图只需输出稀疏线条和边界，不一定需要先建立完整密集 BEV 网格。这篇让图像 token 与少量可学习 map token 共同做 self-attention，再由解码器从压缩表征恢复度量坐标，提供了一个直接可消融的设计。

其价值不只是少 token：同单帧设定下，单向 cross-attention 压缩可能丢失有效信息，联合更新图像与 map token 的方案更好；同时采用减少地理重叠的数据划分，降低静态地图记忆对结果的干扰。这对“紧凑 scene token 能否承载几何任务”有启发，但没有证明能无损恢复稠密 BEV。[方法与实验](https://arxiv.org/html/2610.01905v1)

## 方法与输入输出

多相机、当前及历史图像经共享 backbone 编码，加入可学习的图像行列位置、相机身份和时间 embedding；与 map token 拼接后，通过 **4 层 Pre-LN Transformer**共同更新，随后丢弃图像 token。

默认 **4 个时刻、每相机每时刻 50 个 map token**：nuScenes 六相机对应 **1,200 tokens**，Argoverse 2 七相机为 **1,400**。解码器保留 MapTRv2 的实例/点查询，用 full cross-attention 读取全部 map token，输出道路边界、车道分隔线和人行横道的坐标。

中间 token **没有固定 BEV 网格坐标**；输入也不显式使用内外参、深度或时序自车位姿对齐，几何映射由监督学习获得。可预测几何坐标不意味着 token 可以直接 reshape 成 BEV；依赖 BEV 网格的 occupancy 等任务头仍需适配。[方法第 3 节](https://arxiv.org/html/2610.01905v1)

## 工程判断、局限与建议验证

最值得迁移的是联合 token 压缩与任务查询解码的接口，以及“先做同单帧对照，再加历史”的验证方法。四层 mapper 仍对图像和 map token 做全注意力，FlashAttention 降低显存开销不等于计算复杂度变成线性。

**外参鲁棒性须谨慎解释**：附录 E 只给相机外参数值加噪声；本模型不读取这些参数，因此输出不变。这没有测试相机真实移动后图像变化，也没有测试新的相机布局、车型或焦距。可学习相机身份 embedding 仍可能隐式记住训练配置。

本文还未验证密集 occupancy、跨车几何一致性或整个驾驶多任务系统；额外时序、分辨率和辅助损失差异也限制了把所有表格提升归因于一个模块。尤其 3D 检测附录与 BEVFormer v2 的输入分辨率/时序设定不同，不把其 3.3× 速度差当纯模块收益。

**最值得做的验证**：固定图像 backbone、历史窗口、token 预算和地图解码监督，对比显式 BEV、单向压缩、联合 self-attention 压缩。在真实更换相机姿态或布局的数据上，测地图坐标误差、跨车退化和下游动作质量，再测试是否保留独立几何分支更稳定；不要用修改一份未被读取的标定文件代替跨本体实验。
